# Per-submission execution containment

Implemented 2026-10-30 for audit F01, with the runner half of F12. No provider/account calls, deployment, commits or changes to API routes were made by this task.

## Boundary and caller contract

`src/lib/exec.ts` exports async `runJs`, `runPython`, and `runCpp`, all returning `Promise<ExecResult[]>`. Callers must await **all** languages. Return-value comparison remains `outputsMatch`; C++ retains int/bool/str/vec/vecvec/groups printers and JS retains snake-to-camel names, per-test scope, and Python-style boolean output.

All candidate bytes, including C++ compilation input, execute inside bubblewrap. The host only starts trusted `/usr/bin/prlimit` and `/usr/bin/bwrap`. Each invocation requires separate user, mount, PID, network, IPC, UTS and cgroup namespaces, drops capabilities, disables nested user namespaces, and gets a fresh procfs, minimal devfs, and bounded temporary filesystems. Root, procfs and devfs mounts are read-only; only explicitly bounded work/tmp/shared-memory submounts are writable. There is no in-process evaluation or host-subprocess fallback. No Docker socket is used.

The read-only runtime allowlist is `/usr/bin`, `/usr/lib`, `/usr/include`, optional `/usr/lib64`, the platform's resolved `/bin`, `/lib`, `/lib64`, and the exact running Node executable mounted as `/runtime/node`. These must contain only trusted system software. `/usr/local`, `/etc`, home directories, application source/data, host temporary directories, account files, and service sockets are absent. Submission source is a read-only mount of a fresh private host directory, removed after completion; generated binaries and candidate writes stay on disposable tmpfs. Network namespace isolation denies access to host loopback and external interfaces. Launcher environment contains only a fixed NODE_ENV; bubblewrap clears it again and sets only PATH, HOME, LANG. Candidate environment never inherits web/evaluator/provider credentials.

`ExecutionUnavailableError` (also exported from `exec.ts`) has `code: "EXECUTION_UNAVAILABLE"`, `retryable: true`; `isExecutionUnavailable(error)` identifies it. Sandbox construction, inaccessible/missing runtimes/launchers, failed trusted runtime probes, and concurrency saturation throw this error. **Routes must return retryable 503 and preserve frozen submissions/stages without banking a candidate verdict.** Candidate syntax errors, exceptions, nonzero exits, output/resource limits and hard timeouts produce failed `ExecResult[]` with `actual` beginning `ERROR:`. Runtime probes use actual JS/Python library imports and a trusted C++ compile/link/run before candidate execution. Sandbox errors are redacted rather than exposing host paths.

## Limits

- JS/Python: 3,000 ms candidate wall-clock limit. Trusted preflight is separately bounded at 4,000 ms.
- C++: 15,000 ms total compile/run wall-clock limit, plus 3-second binary timeout inside the sandbox; trusted preflight separately bounded at 4,000 ms.
- Every launch: 12 CPU seconds per process, 2 GiB address space per process, 16 MiB per output file, 64 open file descriptors, zero core dump size. Node additionally uses a 128 MiB old-space heap limit and disables JIT.
- Combined captured stdout/stderr: 256 KiB; overflow kills the launcher process group. `/tmp`: 32 MiB; `/work`: 64 MiB; `/dev/shm`: 4 MiB. Maximum two active submissions **per web process**; additional submissions receive retryable unavailable.
- RLIMIT_NPROC counts host-UID threads. The launcher snapshots current host-UID threads and sets a limit 64 above that baseline. Use a dedicated non-root service UID for a stable bound. A shared development UID can change concurrently, so this is not an exact per-submission process count. Root execution is rejected because root bypasses this limit.
- Host wall timer sends SIGKILL to the detached launcher process group. Bubblewrap's namespace init dies with the launcher, terminating namespace descendants even if they created new process groups/sessions. `--die-with-parent` also covers web process death.

These are OS namespace containment and per-process limits, not a VM or an aggregate memory/cgroup quota. There is no custom seccomp filter. Kernel/runtime vulnerabilities, aggregate memory use by multiple children, and global admission across multiple web workers remain deployment hardening work. Use a dedicated workload host/container with an external memory/PID/CPU quota and request-size/admission controls before an Internet deployment. The cgroup namespace alone does not impose a cgroup resource quota. Harness markers are still candidate-visible, so this change does not make candidate output an independently authenticated grading channel.

## Setup and fail-closed behavior

Run under a non-root UID on Linux with `/usr/bin/bwrap`, `/usr/bin/prlimit`, `/usr/bin/timeout`, `/usr/bin/python3`, `/usr/bin/g++`, Node, standard runtime libraries and C++ headers. Bubblewrap must support `--disable-userns` and `--size`. Unprivileged user namespaces and the other listed namespaces must work under the actual service profile. Verify with `node scripts/execution-containment-check.mjs` **in that environment**, not merely on the Docker host.

Dockerfile installs the necessary tools and runs as `node`. Default container seccomp/AppArmor/user-namespace policies can block nested namespaces; an image build does not demonstrate usable isolation. Configure a narrowly scoped deployment policy that permits the required namespaces, then run the check there. Do not mount `/var/run/docker.sock`, use a privileged web container, or re-enable host evaluation to bypass a failing probe. Unsupported/broken isolation returns retryable unavailable; candidate code is not run. No production container execution has been certified in this task.

`.dockerignore` now excludes `.env*` at every level, runtime `data`/`.codelit`, credential/secret/config directories, common provider account directories, private-key files and build/dependency artifacts. Custom runtime record paths outside those names must also be excluded by the deployment owner. Do not put credentials in the runtime allowlist directories.

## Reproduction and measured evidence

Run `node scripts/execution-containment-check.mjs`. It transpiles only runner modules into an OS temporary directory and removes its disposable source, synthetic app sentinel and synthetic environment variable. It never starts Next, uses stored application records, or invokes an agent/provider. A synthetic Node HTTP server verifies event-loop responsiveness during each looping submission; the parent task owns a full Next/API integration check.

The local bubblewrap probe succeeded with all required namespaces. Initial completed check measured JS 3,087 ms, Python 3,080 ms and C++ 5,164 ms (including compile), all failed as candidate timeout/resource errors. All three languages could not read the synthetic application-owned sentinel or synthetic evaluator environment secret. A Python network probe could not reach the host-loopback test listener. Correctness checks covered all languages, typed collection comparison, camel names, noisy stdout and C++ bool/string/matrix/groups printers. Injected missing launcher and inaccessible runtime returned retryable infrastructure errors with no fallback. Additional detached-child termination checks and final validation results are recorded below after rerun.

Final rerun after read-only root/dev/proc hardening and real runtime preflights: **passed**. Loop wall times: JavaScript **3,182 ms**, Python **3,159 ms**, C++ **6,171 ms** including trusted compiler preflight and candidate compilation. Detached-session Python descendant did not survive namespace termination. Writes to the root/dev mounts were denied, and a file written under `/work` was absent in the next submission. Targeted ESLint passed; the shared connector suite passed **47/47** tests. `git diff --check` passed for modified tracked files. `npx tsc --noEmit` reports only root-owned API integration errors from unawaited async `runJs` in `api/agent-run` and both native session evaluation paths; no runner-module errors remain. Full production build and Next/API retryable-verdict integration remain with the parent/root task once those call sites are updated. Also inspect `api/run`: serializing an unawaited Promise can escape TypeScript diagnostics.
